# Database schema

PostgreSQL 18, database `lion_finance`. Schema changes live in
`backend/src/db/migrations/` and are applied in filename order by `npm run db:migrate`.
Each file runs in its own transaction and is recorded in `schema_migrations`.

| Migration | Purpose |
|---|---|
| `001_initial_schema.sql` | The 13 core tables and basic indexes |
| `002_core_finance_model.sql` | Columns, constraints, triggers and views the application needs |
| `003_reference_data.sql` | Roles, permission codes, default role permissions and settings (no users, no demo data) |

Conventions: money is `NUMERIC(14,2)`, interest rates `NUMERIC(7,4)`, calendar dates `DATE`,
moments `TIMESTAMPTZ`. Allowed values are `CHECK` constraints. Financial rows are never
deleted: payments are reversed, assignments are ended, customers/users/branches deactivated.

## Tables

| Table | What it holds | Key rules |
|---|---|---|
| `branches` | Offices | Unique `branch_code` (A–Z, 0–9, `-`) |
| `roles` | ADMIN, MANAGER, BRANCH_MANAGER, COLLECTION_AGENT, ACCOUNTANT, AUDITOR | Fixed reference data |
| `permissions` | Permission codes checked by the API (`loans.approve`, …) | Fixed reference data |
| `role_permissions` | Which role has which permission | Editable on the Roles screen (except ADMIN) |
| `users` | Staff accounts | Case-insensitive unique email; Argon2id `password_hash` only; lockout counters |
| `user_roles` | Roles per user | |
| `user_sessions` | Server-side login sessions | Only a SHA-256 hash of the session token is stored |
| `customers` | Borrowers | Unique `customer_code` (`CUST-000001`); ID documents store **type + last 4 only** |
| `loans` | Applications and the loan book | Unique `loan_code` (`LN-000001`); lifecycle + approval constraints (below) |
| `collection_assignments` | Agent ↔ loan history | At most one active (`unassigned_at IS NULL`) per loan |
| `collection_schedules` | One row per installment | `due_amount = principal_due + interest_due`; `paid_amount ≤ due_amount`; status matches paid amount |
| `payments` | Money received | Unique `receipt_number` and `idempotency_key`; immutable except reversal; cannot be deleted |
| `payment_allocations` | Which installments a payment paid | Composite FKs force payment, installment and allocation onto the same loan |
| `expenses` | Branch costs | Category list; PENDING → APPROVED/REJECTED with reviewer |
| `audit_logs` | Who did what | Actor, action, entity, safe JSON details, IP |
| `app_settings` | Business settings (JSON) | Validated per key by the backend |
| `schema_migrations` | Applied migration files | |

## Loan lifecycle

```
PENDING ──approve──▶ APPROVED ──disburse──▶ ACTIVE ──fully paid──▶ CLOSED
   │                                          │  ▲
   └──reject──▶ REJECTED                      │  └── payment reversed (re-opens)
                                              └──mark defaulted──▶ DEFAULTED ──fully paid──▶ CLOSED
```

Database constraints enforce: approval fields set once approved; rejection reason set when
rejected; `disbursed_at` set once active; `closed_at` set **iff** CLOSED; CLOSED ⇒ zero balance;
`outstanding_balance ≤ total_payable`; maturity after start.

`total_payable` is a generated column (`principal_amount + total_interest`).
`outstanding_balance` is the amount still receivable (principal + interest) and is updated
in the same transaction as every payment and reversal.

## Installment status

Stored status records payment progress: `PENDING`, `PARTIAL`, `PAID`, `WAIVED`.
"Overdue" depends on today's date, so it is **derived**, never stored (a stored flag would
go stale overnight). Use the view:

```sql
SELECT * FROM v_collection_schedules WHERE effective_status = 'OVERDUE';
```

`effective_status` = `OVERDUE` when the installment is unpaid/partly paid and its due date
is before today (in `APP_TIMEZONE`); `days_past_due` is also provided.

## Integrity guarantees enforced by the database

- **Same-loan allocations:** `payment_allocations(payment_id, loan_id)` → `payments(id, loan_id)` and
  `(schedule_id, loan_id)` → `collection_schedules(id, loan_id)`.
- **Fully allocated payments:** a deferred constraint trigger checks at commit that every
  payment's allocations sum exactly to its amount.
- **Immutable payments:** a trigger rejects edits to amount, loan, date, method, receipt,
  collector or key, and any change to a reversed payment; another rejects deletes.
- **No over-payment of an installment:** `CHECK (paid_amount <= due_amount)`.

Further invariants (balances equal unpaid installments, paid amounts equal recorded
allocations, …) are checked by `npm run db:verify` and the test suite
(`backend/src/db/integrity.ts`).

## Sequences

`customer_code_seq`, `loan_code_seq`, `receipt_number_seq` — codes are generated by the
backend (`LF-20261027-002640` = prefix, business date, sequence).
